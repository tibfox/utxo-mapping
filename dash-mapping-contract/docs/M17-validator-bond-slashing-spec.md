# Spec proposal — M17: validator bond + slashing for false IS attestations

**Audit ID:** M17 (MED 5.0) · "No validator bond/slashing for a false attestation. Feature-wide; `mapinstantsend_v2.go:73-126`."

**Status:** PROPOSAL — not implemented. Needs spec sign-off + governance-contract integration before code can land.

**Author / date:** drafted 2026-06-19 in response to the dash audit follow-up.

---

## 1. Context

The dash mapping contract's fast path (`mapInstantSendV2`) credits wrapped DASH on a BLS quorum signature over an `(raw_tx_hex, instruction, epoch, chain_id, block_height, merkle_proof, tx_index)` bundle. A validator-set entry is `(DID, pubkey, PoP)`; the BLS verify is enforced; the SPV proof is enforced (audit C2); the canonical txid:vout marker prevents double-credit (audit FD3-1). **What is not enforced: validator accountability for signing an attestation that did not happen.**

Concretely, a malicious BLS-quorum (or one corrupted validator who collects enough other signatures via gossip) can sign:
- A `tx_id` that was NEVER broadcast to Dash mainnet, or
- A `tx_id` that was broadcast but never IS-locked, or
- A `tx_id` whose deposit `D` address does NOT actually pay the user's claimed amount.

The first two are blocked post-C2 because the SPV verify rejects bundles without a real Merkle-proof against a chain-relayed header. The third is blocked by the contract's amount-extraction from the raw tx. So the surviving attack vector under M17 is:

**An attacker controls ≥quorum of validator BLS keys and signs a bundle for a tx that is**
**confirmed on Dash mainnet but was NOT generated by a legitimate IS-Login session** —
e.g., an attacker's own deposit they want to credit to someone else's L2 address by lying about the `instruction`.

Today there is **no economic disincentive**. Validators have no bond at stake; rotating them out post-incident is the only response. M17 wants slashing.

## 2. Threat model + slashing trigger

A "slashable event" is: a validator's BLS signature appears on a bundle whose `instruction` field is provably forged.

"Provably forged" means: a fraud-proof submitter posts (a) the attacked tx's raw bytes, (b) the validator's signed bundle, (c) cryptographic evidence the `instruction` does not match the on-chain reality.

The fraud-proof shapes:

**A. Amount mismatch.** The bundle claims paid_amount = X to address D, but `FindOutputAmountAndIndex(raw_tx_hex, D)` returns Y ≠ X. The contract can verify this on-chain by re-running the existing helper.

**B. Stale-epoch attestation.** Validator's claimed epoch is `e`, but the validator was not in the active set at epoch `e`. Contract verifies by re-reading `SaveValidatorSetForEpoch` state.

**C. Replayed signature.** The same validator's signed payload appears in two distinct bundles with different bodies. Standard equivocation proof: post both signatures + both bundle hashes.

Each of these is verifiable on-chain without trusting the submitter; the contract recomputes the check and slashes only if the proof verifies.

## 3. Bond mechanics

Validators already have a `consensus_stake` deposit (governance contract). M17 reuses that stake — no separate IS-attestation bond:

- **Bond source:** validator's `consensus_stake` balance (existing).
- **Bond amount:** spec-defined — proposed start `1000 HBD` per validator (configurable via `pendulumParams`).
- **Slash fraction:** spec-defined — proposed start `25% of bond` per proven offense.
- **Recipients:** burned 100%, OR 90% burn + 10% submitter bounty. The audit cluster's "no fraud-proof bounty" precedent argues for burn; the lack of incentive to submit argues for bounty. Spec call.

## 4. Governance contract integration

The slash trigger needs to actually deduct the bond. Today's governance contract (`vsc.dao`) owns `consensus_stake` mutations. M17 proposal:

1. Add a new governance entrypoint: `slashValidatorForISFraud(validator_did, fraud_proof_bytes, slash_bps)`.
2. The dash-mapping-contract is added as a `TrustedSlasher` in governance — it can call `slashValidatorForISFraud` via the existing `contracts.call_as` host fn pattern.
3. The dash-mapping-contract exposes a NEW entrypoint `submitISFraudProof(proof)` that verifies the fraud-proof shape, computes the slash amount, and `contracts.call_as` into governance.
4. The slash amount comes out of `consensus_stake`; the validator's effective bond drops; if bond drops below `MinISBond`, they're auto-removed from the next epoch's set.

## 5. Spec changes needed

- **Spec §5.3.5 (new):** "IS attestation accountability" — defines slashable events, fraud-proof formats, slash %, withdrawal lockup.
- **Spec §6.1 (extend):** `consensus_stake` is now ALSO bonded for IS attestation; the lockup window for unstake covers the IS-fraud-window (proposal: 7 days post-attestation).
- **Governance contract spec:** add the `slashValidatorForISFraud` entrypoint; add `TrustedSlasher` allow-list.

## 6. Implementation order (suggested)

1. **Spec text** lands first (this document → ratified spec PR).
2. **Governance contract** adds the entrypoint + allow-list (cross-repo work in `gov-contract`).
3. **Dash mapping contract** adds `submitISFraudProof` + the on-chain fraud-proof verifiers. Each proof shape (A/B/C) is its own surgical fn.
4. **Off-chain fraud-proof submitter** — small Go tool that watches the chain, runs the same proof checks, and posts when triggered. Bounty makes this a sustainable role.
5. **Lockup enforcement** — the existing unstake delay needs the IS-fraud-window added.

## 7. Why this isn't landing in the dash audit branch

Each step above is the work of another team (governance contract, spec editor, off-chain submitter). The dash-mapping-contract piece is straightforward — re-run the existing verifiers + call_as — but it can't ship without the governance entrypoint or the spec text. Landing only the contract side would leave a dead entrypoint that fails on the call_as.

So: this document is the deliverable. The team can rank the workstream against other governance items and schedule it.

## 8. Acceptance criteria for the closure

When M17 closes:
- [ ] Spec §5.3.5 ratified.
- [ ] Governance contract has `slashValidatorForISFraud` + `TrustedSlasher` allow-list, dash-mapping-contract is allow-listed.
- [ ] Dash mapping contract has `submitISFraudProof` accepting proof shapes A/B/C (and on-chain verifiers).
- [ ] At least one end-to-end devnet test demonstrating slash trigger → bond reduction → validator removal-from-set.
- [ ] Documentation: operator runbook for the off-chain fraud-proof submitter.

## 9. Open spec questions

- **Slash %:** 25% per offense? Or escalating (25/50/100)?
- **Bounty %:** 0% (pure burn) vs 10% (bounty)?
- **Fraud-proof window:** how long can a proof be submitted post-attestation? Proposal: 7 days. Longer = more recovery time; shorter = faster unstake unlocks.
- **Replay proofs vs equivocation:** treat case C (replay) as 100% bond loss (equivocation is unambiguous fraud)?
- **Forgiveness on slashed validator return:** can a slashed validator re-bond and re-join, or are they permanently banned?

These are decisions for the spec author, not the dash audit run.
